Changelog¶

All notable changes to this project are documented in this file.

The format is based on Keep a Changelog, and this project adheres to Semantic Versioning.

[Unreleased]¶

Added¶

  • A relays line's off= takes cdn:<name> for a CDN in front of that relay which gets nothing through: devices lose that CDN's links and outbounds and keep the relay's others, and a cdn-only relay left with no CDN drops out. Until now a cdn: token voided the whole off= field.

  • A canary checks each CDN in front of the relay it watches, through the CDN as a device's CDN link goes, and gives each under cdn in its facts. The manager hands it the names and CDN path; by hand, set dotdash_cdn_hosts, dotdash_origin_host and the dotdash_cdn_xhttp_path secret.

  • The manager's status prints a line per machine: its release, whether it applied, refused (naming what) or still waits for its newest document, its health, its facts' age and its canaries' verdicts, then the topology. status --wait waits until every machine applied or refused it.

  • The manager's link <device> prints a device's subscription URLs as the servers serve them, its server's and through each own-site relay its pools give it, as QR codes too with --qr. renew <device> gives a device whose link leaked a new id, and prints its new URLs: no ssh to a server for either.

  • The relay's entry-check task tries each of its entries end to end as a device would, REALITY, XHTTP through its site, mKCP and Hysteria2, and says why one fails. The http-origin door keeps each request's address and status in memory, so the check can tell a firewall from docker-proxy hiding the CDN's addresses.

  • A machine's roster entry can name its own credentials, which join hands it in place of the network's, so a relay's credential reaches only its own prefixes on the target. The manager's docs list what each credential needs, and why machines should get no delete.

  • The server's relay-config ends with the count and digest of the devices it hands a relay, and the relay's relay-entry and facts give the same of its own copy, so a stale copy that rejects new devices or still lets in deleted ones shows. The manager's status says when a relay's list isn't the one it sent.

  • The manager's sync and report warn when a server's or relay's site certificate has under 14 days left, from the cert_days in its facts. An expired certificate breaks XHTTP, Hysteria2 and the CDN links while REALITY works, which canaries read as a block.

  • The manager's sync says when servers differ in https_port or in the ports, mKCP header and opener, or presence of XHTTP with REALITY, mKCP and Hysteria2. Each server's subscriptions name the others with its own, so a difference gives devices dead links.

  • The release and dev keys' public halves, in the README and the docs' Releases section: morzer init --signing-key checks even the first release against them, with no access to the repository's variables.

  • An own-site relay's facts carry cert_days, the whole days left on the certificate its site serves, so an authority can warn before it runs out: when it does, XHTTP, Hysteria2 and the CDN links through the relay stop while REALITY goes on. It is left out while Caddy has no certificate.

  • A server's facts carry cert_days, the whole days left on the certificate Caddy serves for its domain, so the authority can warn before a failed renewal breaks XHTTP, Hysteria2 and the CDN paths while REALITY keeps working. Left out while there is no certificate yet.

Changed¶

  • cdn-check also checks a relay's origin= names, and for every CDN name whether its links' path reaches Xray behind it, ends at the site's 404 (a stale path, or a door that refused the CDN), or gets a 5xx or nothing (the CDN doesn't reach its origin). It exits 1 on any of those too.

  • A relays or cdn_extra line, or a field of one, that the server would leave out now fails the change that brings it, by its line number and field, and morzer rolls it back: a new lists health check, which doctor runs too. A field it doesn't know, a taken name or a pool member naming nothing still only warns.

  • The server's cdn_hosts links go by a path of their own (a new cdn_xhttp_path secret), disguised as a relay's CDN links are, so a CDN's logs show neither the direct XHTTP path nor its padding. Devices take them at their next subscription refresh; links imported by hand still work, as the plain path stays.

  • The manager judges a CDN-only relay by its canaries' CDN checks and leaves it out of devices' links once none of its CDNs gets through, where it left it unwatched. Any relay whose CDN gets through is no longer burnt; a CDN failing alone is only reported.

  • The canary's freeze_url, freeze_up_url and download_url take http:// as well as https://, and an https:// one's certificate is now checked. A 64 KB freeze download not done in 40 seconds counts as stopped partway.

  • A relays line with a field the server doesn't know, such as a mistyped cdn_path=, gets a warning naming the field and the line, where the relay used to lose that transport unsaid.

  • A relay's cover app sees each visitor's own address in X-Forwarded-For, where every visitor showed Xray's, so its per-address limits and lockouts no longer hit everyone at once. REALITY hands Caddy each connection behind a PROXY header that only Xray's network may send; the Hysteria2 masquerade still shows Xray's.

  • The cover app behind a server sees each visitor's own address in X-Forwarded-For, not Xray's, so its per-address limits and lockouts hold per visitor. The gate and Xray hand the address on in PROXY headers, which Caddy takes from Xray alone. HTTP/3 visitors still show as Xray.

  • The server's OpenVPN upstream runs OpenVPN 2.6.23, as the client's kill switch does.

Fixed¶

  • The canary's freeze checks and measure's downloads go through the transport they check. They went out over the canary's own network, so where that network froze the test site directly, every path read blocked_by: freeze and the manager took healthy relays out of devices' links.

  • A canary under the hysteria2 profile restarts Hysteria2 when dotdash_id changes, so a rotated id no longer leaves it logging in with the old one.

  • The canary refuses at render a dotdash_server, dotdash_address or dotdash_public_key holding a quote, a backslash, a brace or whitespace, so a value set by the manager can't reach into the canary's Xray config.

  • When the manager can't read a machine's facts, its last good facts stand in for up to a day, and sync prints the read's error. A passing outage of the target, or a wrong identity file, no longer takes every relay off every device in one sync.

  • A canary reading stamped more than ten minutes ahead of the manager's clock no longer counts. One canary whose clock ran ahead could burn a relay alone, and its reading outweighed every honest one until real time caught up.

  • The manager refuses to run with no state file beside a roster that names a joined machine, unless given --new-state. A sync on a checkout the state wasn't copied to made new keys for every server, cutting every device off. adopt still makes the state, as it takes the server's keys.

  • The manager's status shows machines joined with joined as joined, and writes roster.yaml under the state's lock, as sync does. It listed them as not joined, and could rewrite roster.yaml under a timer's sync.

  • A server whose document failed to publish is told again at the next sync to turn hello_split off. The manager forgot it had split a server before publishing, so one failed publish left that server's devices splitting their REALITY hello for good.

  • The manager unsets a relay's via only where an earlier document set it. Every relay whose release takes via was sent the unset, which a relay whose manifest doesn't let a document manage via refuses along with the whole document, so it took no change after join.

  • Each call the manager makes to morzer fails after two minutes without an answer, saying so, and the run goes on as for any failed read or publish. A target that hung held the state's lock, and every timer's sync behind it, for good.

  • The manager's adopt names the devices a server lists as desktop that the roster's desktops lacks. It dropped the kind silently, so after the first sync former desktops got CDN links, some paid by the gigabyte.

  • The manager refuses two machines on one installation id, in the roster or from joined run on the wrong machine. Each then got the other's document on every sync.

  • A relay with REALITY as its only path, whose name is blocked by SNI, is no longer burnt while its canaries get through with the hello split: it gets off=reality and split, so devices' Xray configs keep reaching it, split.

  • A relay that turns CDN-only no longer shows as gone in the manager's report for as long as the log keeps it, nor as burnt for good if it was burnt then. report calls a machine gone only once it leaves the roster.

  • Under direct = false, a client machine fetches its subscription through the first own-site relay its device's pools give it, as the servers choose. The manager took the first own-site relay of all, which could be one the device's pools keep from it.

  • A servers that names no server, such as ,, stopped client-config and the subscriptions with no message. It now means this server alone, as an empty servers does, with a warning.

  • Subscriptions fit about 1000 devices, up from about 10 to 30, on a new 512 MiB in-memory volume that takes only what the files fill. The 4 MiB dotdash_subscription before it is left behind, empty, for sudo docker volume rm dotdash_subscription after the update.

  • A device's subscription URL no longer answers 404 while the service writes the files again after a change: the files of deleted devices or a rotated key go first, and each live one is replaced in place. A full volume now leaves the last files served, where every URL used to go.

  • The docs' recipe for several servers copies kcp_seed and subscription_key too, and says they need the same profiles and transport parameters. Servers set up by the old one gave dead mKCP links to each other, and a 404 to a subscription a relay fetched from the other.

  • A relay run by the manager takes via, via_link and via_fingerprint from it. The relay never declared them managed, so morzer refused the whole document that set or unset them, and such a relay took no change from the manager after join.

  • A relay's http-origin profile without own-site is refused with a message that says to add own-site, in place of a Compose error about a service with no image.

  • A relay's Hysteria2 hands a visitor without a login to its site with the Host the visitor sent, as over TCP. It sent caddy:443, so a cover app's redirects and cookies over HTTP/3 named another host than over TCP.

  • A subscription token the servers don't have gets the relay's own site, as any other path does, where it got the server's 404 page through the tunnel. One request could tell an own-site relay apart, and might name its server.

  • A relay's site names no server anywhere: port 80's redirect and the http-origin door dropped Server: Caddy, as port 443 already did, and every port drops the Via: 1.1 Caddy Caddy adds to what it passes back from a cover app, a server or Xray.

  • A server takes hello_split from the manager's desired state. The server didn't list it as managed, so once the manager's canaries found a server's name blocked by SNI, morzer refused that server's whole document, keys and devices included, until the split was off again.

  • hysteria2_port=53 beside the DNS tunnel is refused when the change is made, as kcp_port=53 is, rather than failing when the gate publishes both on UDP 53.

  • Under the hysteria2 profile, a visitor over HTTP/3 reaches the cover site with the domain as its Host, as over TCP. Hysteria2's masquerade sent caddy:443 in its place, so an app's redirects and cookies over HTTP/3 named caddy.

  • The server's redirect to HTTPS on port 80 no longer sends Server: Caddy, which the site's own answers on 443 already left out. It is otherwise the redirect Caddy makes itself.

  • With cover naming an app, the site's answers no longer carry Via: 1.1 Caddy, which Caddy adds to whatever it proxies and which named it as Server would.

  • A client under tun with no link that answers, as on a fresh install or with kept links whose server is gone, now gets its subscription: while no link answers, the fetch goes directly from Xray, outside TUN. Before, it entered TUN, found no link and was refused for good. No other process can take that way out.

  • A client that starts on its kept links, because the subscription can't be fetched, fetches again every 30 seconds until it gets through, not a whole subscription_interval later. Kept links whose server is gone give way to the new ones within a minute.

  • The client's kill switch keeps its rules while dotdash-client is updated, restarted or stopped, so the machine never gets out around dotdash then; leaving tun still takes them out, even after a stop. doctor now checks IPv6's rules too. The client's tun page shows a unit that closes the gap at boot.

  • Under tun, DNS to any resolver not on the machine, such as the router DHCP named, gets fake addresses like the rest, whoever asks: any user, systemd-resolved, a container. It goes nowhere while Xray is down. The kill switch redirects it with nftables.

  • A client's DOMAIN-REGEX rule keeps its commas, as in ^a{2,3}. It was cut at the first one, which Xray refused, so the change rolled back.

Security¶

  • The manager refuses facts no bundle prints: whitespace, quotes, backslashes, braces or control characters in a value, or a field missing or of the wrong type. A tampered relay can no longer add lines to the servers' relays, crash every sync or write to the terminal, nor take another relay's address out of the pools.

  • A device taken out of the manager's roster loses its id at the next sync, so added back it gets new links and a new subscription URL, and its leaked ones let no one in. Before, it got the same id and token back. Relays' and canaries' own ids and client machines' passwords are dropped the same way.

  • After rotate finish, the manager's next sync removes the retired REALITY key and its short id from every server's secret store, so later backups no longer hold them. Before, the old key was only turned off.

  • bootstrap.sh runs morzer's installer from a pinned commit, checked by sha256, where it piped whatever a movable tag served into sh. It also trusts Docker's apt key only when the file holds that one key, by its fingerprint.

  • A server takes a relays line only when its host, site, public key, short id, VLESS encryption and XHTTP path each have their shape, and gives no mKCP link through a kcp= field that isn't whole. A bad line is left out and named by its line number, so a tampered one can't rewrite or break every device's config.

  • servers and cdn_hosts entries that aren't host names are left out with a warning, and an xdns_domain that isn't one stops client-config, instead of reaching every device's links and Xray config.

  • With direct=false, subscriptions carry no title (Profile-Title), which names the exit in Happ and Hiddify: with a direct line in upstreams it was the server's own address, shown to every device that direct=false keeps it from.

  • A relay refuses a quote, backslash, brace or whitespace in site, dotdash_servers, dotdash_address, dotdash_public_key and each via line, set by hand or by an authority. Such a value could add keys to its Xray config or lines to its Caddyfile; the apply now fails and the relay stays as it was.

  • acme-dns takes no new registrations by default, as anyone reaching its port 443 could register. To register a parent, sudo morzer config set registration=true, run register, then set it back to false; register says so. Existing registrations keep working.

  • Under the server's openflux profile, the exits' connections go through Xray, so the rules devices get apply to them: BitTorrent and trackers, mail on port 25, private addresses and the server's networks are blocked, and resolve and ipv6 hold. They went to the gate, past all of it.

  • resolve=upstream beside a direct upstreams line is refused: the apply rolls back and doctor names it. The gate resolved devices' names on the server, so a device reached its containers by name, xray and gate among them, past Xray's rules. Use resolve=gateway.

[0.17.0] - 2026-11-25¶

Added¶

  • cdn_extra on the server: the XHTTP settings a CDN or its gateway asks for, by name, pasted as the CDN gives them. Links and outbounds through that name carry them in place of dotdash's own, so a CDN that wants its own settings needs no change to dotdash. Settings Xray refuses are left out with a warning. The manager's roster takes cdn_extra too.

  • A device's kind, desktop or mobile, after its name in vless_clients. A desktop gets no CDN link: none through the server's cdn_hosts, none through a relay's cdn= or origin=, and nothing through a relay that offers CDN links alone. CDNs serve restricted mobile networks, some paid by the gigabyte, where a desktop moves the most. A changed kind reaches the device at its next subscription fetch. The manager's roster takes desktops, a list of its devices. Servers and relays take such lines from this release on: update the relays before giving a device a kind, and take the kinds off before rolling back to an earlier release, whose image refuses them.

  • An openflux profile on the client: when every dotdash link fails its probe, Xray's balancer hands the traffic to an OpenFlux client, which reaches this device's OpenFlux exit on a dotdash server (the server's openflux profile) over a room or call on a service the network still lets through. The link goes in a new openflux_link secret, as the server's openflux-link task prints it. The traffic goes back to the links once one answers its probe again. It serves the proxy port, not tun.

  • An openflux profile on the server, the way in left when nothing else gets through: an OpenFlux exit for each device listed in openflux_channels, which that device's OpenFlux app meets on a room or call of a service a restricted network still lets through. Each exit opens the device's connections through the gate, so they leave through the upstreams; UDP goes the same way, or nowhere with upstream_udp off. Only the carrier's own connections leave directly. A line names its carriers by short kinds: co makes its own rooms, and tm its own call with the new call_provider and call_token, or takes a call link of yours. Each device's key, rooms, call and link are kept on a volume, and a device deleted from vless_clients loses them. The openflux-link task prints the link for the app. OpenFlux 0.17.1, from platform-images' openflux image. In the lab tm carried 8 Mbit/s with no stall but 2.3 Mbit/s even idle, co 1-2 Mbit/s; the exit's OpenFlux version must match the apps'.

  • A device-traffic profile on servers and relays: Xray counts the bytes each device moves, and the facts carry the counts by device name to the authority. The manager adds them up by day and names a device whose day reached five times its median and at least 2 GB, as a link passed around shows: sync for yesterday and today, report for the last 30 days. Only counts, never an address, and not in the metrics files. Xray counts a device by its name, so a vless_clients line with no name isn't counted; the manager names every device. A relay counts its own devices, which the server sees as the relay alone. The facts task, with the other tasks of its service, runs in Xray's namespace under the profile.

  • happ_routing on the server: a routing profile in Happ's own JSON, which every subscription then carries in Happ's routing header (relays' too). Happ adds it and turns it on, so the sites it lists as direct go around the tunnel on every Happ device. Other apps ignore it.

  • The canary ends its facts with a burst through REALITY: six connections at once, then one more (burst_check, on by default). A network that freezes a device opening several connections to one address within a fraction of a second freezes REALITY with Vision on every page while a check of one connection passes; the canary now reports REALITY down there, with burst: true and blocked_by: burst, and the manager takes REALITY off that relay's links as for any blocked path.

Changed¶

  • A relay's http_origin_host takes several names, comma-separated, for a rented CDN that gives more than one, such as a spare for when one is blocked. Devices get a 4 KiB relay · cdn link and outbound through each, numbered with the relay's other CDN links: relay · cdn 1, relay · cdn 2. A name may carry a path of the CDN's own, <name>/<path>, which its links take in place of the CDN path. The server and the manager read the list from the relay's line as they read one name.

  • Servers' and relays' facts run again before every fleet publish, hourly (morzer's published.refresh), so the device-traffic counts reach the manager within the hour. Without the profile their output stays the same and so do the facts; each run is one task operation in the journal and the attestations (retention.attestations).

Fixed¶

  • A relay's relay-entry prints the http-origin door's port and the xhttpSettings for the CDN's form again. 0.16.0 never handed the task the port, so it printed neither, and the line carried no cdnpath= until http_origin_host was set.

[0.16.0] - 2026-11-24¶

Added¶

  • A relay's http-origin profile: a door in plain HTTP on http_origin_port for a CDN that ends TLS at its own edge and fetches the origin unencrypted, as some rented for restricted networks do. It answers only the gateway addresses in http_origin_from, and only on the CDNs' path, which it passes to Xray's XHTTP inbound. http_origin_host reaches the server's line as origin=, and devices get a relay · cdn link through it uploading 4 KiB at a time. relay-entry prints the port and the xhttpSettings to give the CDN. The manager carries origin= too.

  • client-config --local-auth prints the Xray config with a password on its local SOCKS, the same on every run, and no local HTTP proxy, for v2rayNG's "Local proxy username and password". Other apps on the phone then find no open proxy to try. devices.md says how to do the same in v2rayNG with links or a subscription.

  • tunnel_host on a relay: one host a cover app may call at http://caddy:8090. Caddy sends the calls on as HTTPS inside the link to the servers, or to the relays in via, so the relay shows one TLS client, Xray's, where an app calling the host itself showed its own beside it.

  • A subscription asks the apps that read Profile-Update-Interval (Happ, Hiddify) to fetch it again every 6 hours, so new relays, rotated keys and revoked devices reach them without a manual refresh. A relay's subscription carries it too.

Changed¶

  • A relay's cover app goes on dotdash-relay_edge, a network of its own with Caddy, as dotdash_edge is on a server. On dotdash-relay_default it shared Xray's network, where it could reach the subscriptions proxy into the tunnel and the XHTTP inbounds. An app already on dotdash-relay_default keeps working, and doctor names it until it moves.

  • The server drops announces to public BitTorrent trackers, by the trackers' names, and mail on port 25, beside the BitTorrent handshakes it already dropped. Upstream providers forbid both, and an announce puts the line's address in public swarms. Encrypted peer connections still look like any other traffic.

Fixed¶

  • The manager's join gives a machine installed before it joined the recovery recipient too, as init gives a fresh one, so its backups can be decrypted once the machine is gone. It already got the backup target.

[0.15.0] - 2026-11-23¶

Changed¶

  • client-config's Xray config answers devices' DNS with fake DNS, as dotdash-client's TUN does: a name gets a stand-in address at once and the server looks it up, so a first visit to a name no longer waits for a lookup through the tunnel (53 ms less in the lab). dns_resolver is now the server's alone.

[0.14.0] - 2026-11-23¶

Added¶

  • A relay can go through other relays instead of the servers: via takes their lines as relay-entry prints them, reached by REALITY or, with via_link=xhttp, XHTTP through their own sites. The servers never see its address, for a relay on an address worth keeping. The manager's roster takes both.

  • standby at the end of a relay's line in relays keeps that relay idle while others get through: devices get its links last, and their Xray configs, dotdash-client's included, don't check them and use them only once every other link fails. The manager's roster takes standby on a relay.

  • A direct line in upstreams makes the server's own address a way out, for a server already on a residential line: alone, or beside proxies as their backup or fallback. doctor asks it from the server itself.

  • dotdash-manager adopt takes a running server's keys and its devices' ids, so a network set up by hand moves under the manager without devices getting new links or subscription URLs.

  • dotdash-manager join prints a script to pipe over ssh, and joined keeps the id and key it prints back. Nothing goes into the roster by hand, and a machine installed already is only pointed at the manager.

Changed¶

  • The server's gate, the relay and the warm container probe each connection's path MTU and hold at most 128 KiB unsent per connection. A path that silently drops large packets no longer stalls every TCP link (Vision's first byte 332 ms instead of never), and a click waits less behind a download on XHTTP.

  • Every TCP link in a device's Xray config, and the relay's link to its server, gives up a connection after 15 s of unacknowledged data and redials. When a censor freezes a connection, XHTTP answers again after 17 s instead of a minute.

  • A Hysteria2 connection a network froze is given up after 15 s of silence instead of 30, and the device reconnects: it answers again after 16 s instead of 31. The Xray config devices get sends keepalives, so a healthy connection idle that long stays open.

  • The gate times out an upstreams line's probe after 1.5 s (Xray's burst observatory) rather than 5. A line throttled hard but still answering, which added a second to every connection, now counts as down and the next one carries the traffic.

  • When no upstreams line answers its probe, the gate sends connections through the first line instead of failing them, so a wrong verdict, or a single line that is only slow, no longer stops the traffic. Nothing leaves directly.

  • Every apply, update and doctor refuses upstream_udp=true while an upstreams line is an HTTP or HTTPS proxy, which drops UDP. The policy check also reads a line's group= and kind when name= and group= come before its URL.

  • The Xray config devices get (client-config --full, the subscription's JSON, dotdash-client) shares UDP flows over a few connections on REALITY links (XUDP Mux): one connection for 20 flows instead of 20, each later flow answering in one round trip instead of three.

  • The DNS tunnel sends every 50 ms (xdns_tti), not every 200: about three times the speed. Devices' configs spread its queries over three resolvers (xdns_resolvers), so each sees little more than before.

  • Hysteria2 no longer answers a stray packet with a stateless reset, which the site's own HTTP/3 never sends and a prober could tell apart.

  • Devices' and relays' configs probe each link at a moment of its own (burstObservatory), not all together, which tied a device's links to each other for an observer. Picking the fastest works as before.

  • Every Xray container sets Go's soft memory limit (GOMEMLIMIT) at about 90% of its memory cap, so Go collects garbage harder near the cap instead of the kernel killing Xray.

  • The server's gate and a relay send to devices on BBR, in their own containers only (tcp_congestion). On a lossy last mile it kept 6-50 times cubic's speed in the lab. Set tcp_congestion=cubic on a kernel without tcp_bbr, where the apply would otherwise fail and roll back.

  • A server that resolves names itself (resolve=gateway), and the Xray config client-config prints, answer a name looked up before from the cache at once, even after it expired, and ask again in the background, for a day at most. A site revisited no longer waits for a lookup through the upstream.

  • dotdash-client runs Xray instead of mihomo. It asks the subscription URL for the device's Xray config and uses whichever outbound answers fastest. Update the server first: an older one serves no config, and the client then refuses traffic rather than send it around dotdash.

  • dotdash-client's rule parameters keep their form. A line whose type isn't DOMAIN, DOMAIN-SUFFIX, DOMAIN-KEYWORD, DOMAIN-REGEX, GEOSITE, IP-CIDR, IP-CIDR6, GEOIP or DST-PORT stops the change, naming the line. IP rules never look a name up, so no-resolve changes nothing.

  • The server and the relay need morzer 0.18.0. Before an apply starts them, it checks each port they publish on that port's own address and protocol, the UDP ports of the DNS tunnel, mKCP and Hysteria2 included, and refuses to start with one taken, naming it, rather than failing after the old containers stopped.

  • dotdash-acme-dns needs morzer 0.17.1, which backs up a machine set up without a recovery key, so updates there no longer depend on the placeholder secret the bundle carried; the secret is gone.

Fixed¶

  • dotdash-client under tun no longer sends traffic around dotdash while Xray is down, after a crash or on the restart for a new subscription. A kill switch keeps routing rules that let only Xray's own connections and the LAN out then, and doctor checks them.

[0.5.0] - 2026-11-10¶

Added¶

  • Every bundle ships the key it is signed with, so morzer init needs no --signing-key: it prints the key, trusts it, and requires every later release to be signed by it. --signing-key still checks even the first release against the repository's.

  • A relay for networks that let only some addresses through: dotdash-relay, a new bundle released with dotdash, carries devices from a machine inside that network on to this server over port 443. The relay-config task prints its setup; its line in the new relays parameter adds a link through it for every device.

  • A client for a Linux machine or a network: dotdash-client, a new bundle released with dotdash, runs mihomo from one device's subscription URL, refreshed through dotdash, with a SOCKS5 and HTTP proxy port, block and direct rules, and a password once the port is published beyond the machine.

  • dotdash-client's tun profile sends every connection on the machine through dotdash with no proxy settings, its containers' and IPv6 included, with DNS answered by fake addresses whose names dotdash resolves; nothing gets out around dotdash when it is out of reach.

  • Under tun, dotdash-client can be its LAN's gateway: devices that use it as theirs go through dotdash too. gateway=true has doctor check that the host forwards the LAN into TUN, naming the two DOCKER-USER rules a FORWARD policy of DROP needs, and dns_listen answers the LAN's DNS.

  • mihomo connects over REALITY and XHTTP with REALITY: those links now carry support-x25519mlkem768=true, without which mihomo leaves out the key share Xray's REALITY requires and fails with "REALITY authentication failed". Other clients pass over the parameter.

Changed¶

  • Every bundle of this release needs morzer 0.15.0: run sudo morzer self-update before updating. An older manager refuses the release and changes nothing.

  • The DNS tunnel and XHTTP with REALITY run together as installation.profile=xdns,xhttp-reality, two profiles combined.

  • upstream6 is no longer generated as a placeholder: a fresh install has none until the IPv6 proxy is turned on. An existing value is kept.

  • Unattended updates apply releases again, and morzer rollback works again, both of which 0.4.0 turned off for its own change of the upstream settings. An update from 0.3.x is still refused until the upstream secret is set.

  • bootstrap.sh is served from the documentation site: curl -fsSLO https://morzecrew.github.io/dotdash/bootstrap.sh. The documentation itself moved from the README to https://morzecrew.github.io/dotdash/, one version per release.

Deprecated¶

  • The xdns-xhttp-reality profile: xdns,xhttp-reality deploys the same. It goes in the next release.

Fixed¶

  • bootstrap.sh installs morzer 0.15.0, which the bundles require. It installed 0.13.0, so init on a freshly prepared host refused the release until morzer self-update.

[0.4.0] - 2026-11-08¶

Changed¶

  • The upstream proxy is one secret, upstream, holding user:pass@host:port, so changing proxy is one restart; upstream_host, upstream_port, upstream_username and upstream_password no longer work. Run sudo morzer secret set upstream before updating: an update without it is refused.

  • This release is never applied unattended, and morzer rollback from it is refused, since 0.3.x could not start without the old settings; the pre-update backup is the way back.

  • The IPv6 proxy is the upstream6 secret in the same form, turned on by upstream6_protocol (socks or http, now none by default) instead of upstream6_host. With it on, set upstream6 and upstream6_protocol before updating, or IPv6 goes back to the first proxy.

  • Links are named after the device and transport, such as phone [reality], phone [xhttp] and phone [xhttp+reality], in place of dotdash-phone, dotdash-xhttp-phone and dotdash-xhttp-reality-phone. Apps show the new names once the links are added again, or at the next subscription refresh.

  • With subscriptions on, client-config prints each device's subscription URL alone, so the output stays short; --full before the device's name (-- --full phone) adds its links and Xray config, as before. With subscriptions off it prints what it always did.

  • The subscription service reports healthy only once every device's subscription is written: an apply or an update waits for it, and doctor names the service when that never happens.

[0.3.0] - 2026-11-08¶

Added¶

  • Optional subscriptions (subscription): each device gets a URL on the cover site that serves its links, which client-config prints and the app refreshes by itself, so a revocation or a key rotation reaches devices without resending links. Rotating subscription_key moves every URL.

  • An optional second proxy for IPv6 (upstream6_host, with its own credentials), for an upstream that leaves over IPv4 only: destinations with an IPv6 address, sites with both included, leave through it, and the rest through the first. Neither falls back to the other, and doctor names the one that fails.

Changed¶

  • The Xray config client-config prints checks all its entries at once every 30 seconds, where it checked one a minute in turn, so it leaves an entry that stops answering within about half a minute instead of up to several minutes. That is two small requests a minute per entry.

[0.2.0] - 2026-11-08¶

Added¶

  • The exit-check task prints the IPv4 and IPv6 addresses the upstream leaves from, each with its network and country, and says whether IPv6 is unavailable or leaves from another network than IPv4. It changes nothing.

  • Every apply and update, and every doctor, checks the release's invariants against what runs: traffic leaves through the upstream only, every inbound demands a client, and only the bundle's own ports are published, by unprivileged containers. An update that breaks one is rolled back; drift fails doctor.

  • An optional third transport: XHTTP under REALITY instead of TLS, on a port of its own (xhttp_reality_port, 8443). The xhttp-reality profile turns it on, xdns-xhttp-reality with the DNS tunnel; client-config then prints a third link and outbound, and the first two as before.

  • The canary's measure task fetches a URL through each transport N times and prints, as JSON, how many succeeded, timed out or failed, and the latency of those that succeeded.

  • The canary's xhttp-reality profile checks XHTTP with REALITY beside REALITY, on the server's xhttp_reality_port.

  • Both bundles carry signed build provenance, naming the commit and workflow run that built them. Check it with gh attestation verify oci://ghcr.io/morzecrew/dotdash:<version> --owner morzecrew, beside the signature morzer verifies.

  • With several servers (servers), canary-config also prints how to point a canary at each of the others: they share the secrets, so only server and address change.

  • The Xray config client-config prints answers the device's DNS, in an app's VPN or TUN mode, over DNS-over-HTTPS (dns_resolver) through the tunnel, with IPv4 addresses only: lookups no longer reach the local network's resolver or need the upstream to relay UDP. The README covers each app.

Changed¶

  • Both bundles need morzer 0.14.0 or later. sudo morzer secret edit vless_clients then opens the list as plain text, one client per line, and init needs no --product.

  • When the way out fails, doctor says which layer did: the upstream proxy's address, its credentials, the destination behind it, or an exit that no longer matches healthcheck_expect. The health checks are now cover-site and egress.

  • Xray's log_level defaults to error. At warning and below it names the destinations of failed connections, which a log should not keep; set it back for debugging.

  • client-config prints one complete Xray config per device, for one server too: it uses whichever of REALITY and XHTTP answers fastest on any listed server, and the DNS tunnel only when none answers, instead of printing the tunnel's outbound alone.

Fixed¶

  • The cover site's error answers, such as 404 and 405, no longer name the server, and carry the site's headers like its pages do. A prober could tell them apart.

  • The canary's xhttp profile applies. Its Compose file found the base file by a path relative to a directory morzer does not run Compose from, so the profile failed validation.

  • A failed first apply, of dotdash or the canary, no longer leaves a directory where Xray's rendered configuration goes, which made every later apply fail to render it. A missing configuration file or Caddyfile now stops the container from starting instead.

Security¶

  • The upstream no longer learns which hostnames clients visit: this server resolves them over DNS-over-HTTPS sent through the upstream (resolve=gateway, the default) and hands it addresses only. A name resolving to a private address is blocked; resolve=upstream restores the old behaviour.

  • Xray has no route out of the machine. It runs on internal networks only, and a small gate container forwards the public port to it and carries its traffic to the upstream, whose credentials only the gate holds. Whatever Xray's own config says, it cannot send traffic past the upstream.

  • Caddy no longer writes the XHTTP path, a secret, to its log: it logs errors only, and never the request they concern, so no URI, header or client address either. An XHTTP session cut off mid-response used to log all three.

[0.1.0] - 2026-11-07¶

Added¶

  • A morzer bundle for one Docker host, published as ghcr.io/morzecrew/dotdash: releases as :X.Y.Z and :stable, signed with the release key, and every change to main as :main, signed with the dev key. Requires morzer 0.13.0, Docker 28 and Compose 2.35, or later.

  • REALITY on port 443: a client holding the key reaches Xray over VLESS with Vision, and anything else reaches a Caddy cover site with a Let's Encrypt certificate. https_port moves both to another host port.

  • XHTTP over TLS behind one secret path of the cover site, which also works through a CDN that proxies HTTP/2 to the server.

  • An optional DNS tunnel on UDP/53, VLESS over mKCP with XDNS, for networks where only DNS gets through. The xdns profile turns it on, at install or later; its zone is t.<domain> unless xdns_domain names another.

  • Every inbound uses VLESS Encryption (ML-KEM-768). morzer generates every key, short id and path at install, so no secret is chosen by hand.

  • All client traffic leaves through an upstream SOCKS5 or HTTP proxy you provide, optionally over TLS, with no direct fallback. UDP is relayed only through a SOCKS5 upstream that supports it (upstream_udp).

  • Xray is healthy only while it fetches a URL through the upstream, and doctor fails while it cannot. With healthcheck_expect, a response that does not match, such as a changed exit IP, fails it too.

  • An apply or update succeeds only once port 443 serves the cover site with a certificate a browser trusts.

  • The client-config task prints each device's REALITY and XHTTP links, and the DNS tunnel's outbound when it is on. With servers naming servers that share the keys, it prints links for each and an Xray config that uses whichever answers fastest.

  • One VLESS id per device in vless_clients: deleting a device's line revokes that device alone.

  • The cover site serves your own static files from site_dir wherever they have the requested path, and otherwise a bundled page titled with the server's domain.

  • cert_issuer=internal takes the certificate from Caddy's own CA instead of Let's Encrypt, for a machine the internet cannot reach.

  • Unattended updates: the bundle declares that it keeps no database and is safe to roll back, which morzer requires before it installs a release on its own. Nightly backups include Caddy's certificates.

  • The canary-config task prints the init command and secrets for a dotdash-canary machine acting as one of the clients.

  • dotdash-canary, a second bundle released with dotdash as ghcr.io/morzecrew/dotdash-canary, for a machine inside a network you care about, such as a box at home. It connects to a dotdash server as an ordinary client and needs no open port.

  • The canary's health check fetches probe_url through dotdash over REALITY, and with the xhttp profile also over XHTTP, in up to three tries. doctor fails when all three fail, so a notify target at its default level hears that the network lost its way out.

  • Services run as a non-root user in read-only containers with every capability dropped. Xray's access log is always off.

  • scripts/bootstrap.sh prepares a fresh Debian or Ubuntu server: Docker, sops, age and morzer, unattended security updates, and SSH with keys only once an authorized key exists.
