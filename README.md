# dotdash

A [morzer](https://github.com/morzecrew/morzer) bundle that runs an Xray gateway
on a single Docker host: REALITY on port 443 in front of a website served by
Caddy, optional DNS-based and XHTTP-with-REALITY entry points, and all
outbound traffic routed through an upstream proxy you provide.

## Channels

| Tag | |
| --- | --- |
| `ghcr.io/morzecrew/dotdash:main` | every push to `main`, signed with the dev key; may be broken |
| `ghcr.io/morzecrew/dotdash:stable` | releases: a `vX.Y.Z` tag on `main`, signed with the release key |
| `ghcr.io/morzecrew/dotdash:X.Y.Z` | one exact release |

## Install

Requires a domain whose DNS you can edit (any provider), a Linux host with
Docker ≥ 28 and Compose ≥ 2.35, `sops`, `age`, morzer ≥ 0.13.0, and upstream
proxy credentials. `example.com` below is your domain.

**1. DNS**: `example.com  A  <server IP>`.

**2. Server**: open 80/tcp and 443/tcp (80 is for the certificate). Docker's
published ports bypass ufw and firewalld, so the host firewall guards only the
rest, SSH included: allow keys only (`PasswordAuthentication no`). On a fresh
Debian or Ubuntu server, `scripts/bootstrap.sh` installs everything above but
the domain and credentials, turns on security updates, and sets SSH to keys
only once an authorized key exists:

```sh
curl -fsSLO https://raw.githubusercontent.com/morzecrew/dotdash/main/scripts/bootstrap.sh
less bootstrap.sh && sudo bash bootstrap.sh
```

Installing morzer yourself, give its `install.sh` `--dir /usr/local/bin`, as
`bootstrap.sh` does: run as your user it picks `~/.local/bin`, which `sudo`
does not search, and morzer's timers run the binary from where it was put.

**3. Deploy**

```sh
morzer secret recipients generate-recovery-key ~/dotdash-recovery.key   # store off the machine
sudo morzer init --product dotdash --release oci://ghcr.io/morzecrew/dotdash:stable \
  --require-signature --signing-key "$MINISIGN_RELEASE_PUBKEY" \
  --domain example.com --recovery-recipient age1… \
  --set upstream_host=proxy.provider.example --set upstream_port=1080
# also --set upstream_protocol=http, --set upstream_tls=true if the proxy needs them

sudo morzer secret set upstream_username
sudo morzer secret set upstream_password
sudo morzer apply
```

Spell `--product dotdash` exactly: morzer names the variables it hands the
bundle after the installation, and the bundle reads `DOTDASH_*`
([morzecrew/morzer#298](https://github.com/morzecrew/morzer/issues/298)). It is
needed at all only because morzer reads the name from a local release alone
([morzecrew/morzer#297](https://github.com/morzecrew/morzer/issues/297)).
Before the first `apply`, each `secret set` reports that it restarted nothing;
the value is stored.
`MINISIGN_RELEASE_PUBKEY` is this repository's variable of that name
(`gh variable get MINISIGN_RELEASE_PUBKEY -R morzecrew/dotdash`). If the package
is private, log root's Docker in to ghcr first.

Keys, ids and paths are generated by morzer, and Caddy gets a Let's Encrypt
certificate on first start. `apply` succeeds only once Xray has fetched a URL
through the upstream proxy and port 443 serves the site with a trusted
certificate.

**4. Clients**

```sh
morzer task run client-config --output             # every client
morzer task run client-config --output -- phone    # one
```

Prints a REALITY link (v2rayN, v2rayNG, Hiddify, Happ, Streisand) and an XHTTP
link, and one Xray config for v2rayN or v2rayNG (custom config) that uses
whichever of the two answers fastest and, when the DNS tunnel is on, falls back
to it only when neither does. Treat the output as a password. To scan a link
with a phone, show each as a QR code in the terminal (`qrencode` package):

```sh
sudo morzer task run client-config --output -- phone | grep '^vless://' |
  while read -r link; do qrencode -t ansiutf8 "$link"; done
```

Each device should get its own id. `sudo morzer secret edit vless_clients`
opens the list as YAML, one `<uuid> [name]` per line of a `|` block
(`uuidgen` makes an id); without the `|`, YAML joins the lines into one:

```yaml
vless_clients: |
  e3532f3a-a23d-4bb0-ba7e-db8ba3ccd740 laptop
  0b8f6f4e-5c1d-4a2b-9e3f-7d6c5b4a3921 phone
```

It opens `$EDITOR`, which `sudo` drops, so `vi` unless you pass one:
`sudo EDITOR=nano morzer secret edit vless_clients`. Add a line for a device
and delete it to revoke the device; Xray restarts on save. A revoked
device still knows the shared keys. If it must not even recognise the server,
also rotate `reality_key` and `vless_seed` (`morzer secret rotate <name>`) and
resend every device's links.

### Cover site

Anyone reaching port 443 without the REALITY key sees a website, and gets
exactly what Caddy alone would answer, whatever they send; CI probes for it.
The weak spot is the bundled page: it differs between servers only in its
title, so whoever has seen one dotdash server can find the others by the
rest. Give each server a site of its own before handing out links: put static
files in `/srv/dotdash` (the `site_dir` parameter), readable by uid 65532.
Caddy serves them wherever they have the requested path, and the bundled page
otherwise, with no restart. Several pages that look maintained blend in
better than one.

### DNS tunnel (optional)

Delegate `t.example.com` to the server, open 53/udp, and add `--profile xdns`
to `morzer init` in step 3, or turn it on later with `sudo morzer config set
installation.profile=xdns`. For another zone, set `xdns_domain=<zone>`. If
`systemd-resolved` holds port 53, set `xdns_bind` to the public IP.

```text
ns.example.com.  A   <server IP>
t.example.com.   NS  ns.example.com.
```

A zone under a domain of its own is better, such as `--set
xdns_domain=t.example.net` delegated from `example.net`: a resolver that flags
tunnel queries flags the domain they are under, and blocking it would take
`example.com` with it.

### XHTTP with REALITY (optional)

A third link: XHTTP, as in the second, but under REALITY instead of Caddy's
TLS, on a port of its own (`xhttp_reality_port`, 8443 unless set). It suits a
network that lets another port through better than 443; it is not faster or
harder to block by design, and a canary's `measure` shows how it does from a
given network. Clients built on Xray-core take it, such as v2rayN and v2rayNG.
Open the port and switch to the profile that adds it:

```sh
sudo morzer config set installation.profile=xhttp-reality        # with the DNS tunnel: xdns-xhttp-reality
sudo morzer task run client-config --output
```

The first two links stay as they were. To turn it off, set the profile you had
before: `installation.profile=xdns` with the DNS tunnel, or `sudo morzer
config unset installation.profile` without. Do that before rolling back to a
release that has no such profile, which morzer otherwise refuses.

### CDN (optional)

The XHTTP link also works through a CDN that proxies HTTP/2 to
`https://example.com`: put the CDN's name in the link's address. If the CDN
proxies `example.com` itself, use the server IP in the REALITY link. Check the
CDN's terms first; some, Cloudflare's self-serve plans among them, prohibit
proxy services.

### Several servers (optional)

Clients can switch to another server when one stops answering. Install dotdash
on each server under its own domain, copy the first server's keys to the
others, and list them all on every server. Use the same `https_port`
everywhere.

```sh
# on the first server; sudo on b.example.com must not prompt
for s in vless_clients vless_seed reality_key reality_short_id xhttp_path; do
  sudo cat /run/dotdash/secrets/$s | ssh b.example.com sudo morzer secret set $s
done
# on every server
sudo morzer config set servers=example.com,b.example.com
```

`client-config` then prints links for each server, and its Xray config uses
whichever server and transport answers fastest. Add and revoke devices on
every server.

## Keeping it running

**Updates.** To install each release from `:stable` unattended, nightly at
03:30 unless `update.schedule` says otherwise:

```sh
sudo morzer config set update.check=true
sudo morzer config set update.channel=oci://ghcr.io/morzecrew/dotdash:stable
sudo morzer config set update.auto_apply=true
```

This hands whoever holds the release key root on the machine, since hooks run
as root; the install above already requires that key's signature. A release
that fails to install is not retried, and `morzer status` says so. See morzer's
[unattended updates](https://github.com/morzecrew/morzer/blob/main/pages/docs/operating/unattended-updates.md).

**The manager.** A release may need a newer morzer than the machine runs, and
is refused until it has one. `sudo morzer self-update` installs the newest,
checked against the signing key built into the running one.

**Backups.** morzer backs up every night: the secrets, encrypted to the
recovery key, and Caddy's certificates. They stay on the machine until it has a
target; `file://` and `ssh://` work too. See morzer's
[backups](https://github.com/morzecrew/morzer/blob/main/pages/docs/operating/backups.md)
and [recovering a lost machine](https://github.com/morzecrew/morzer/blob/main/pages/docs/operating/recovering-a-lost-machine.md).

```sh
sudo morzer backup target add s3://bucket/dotdash --credentials backup_s3
```

**Alerts.** A target receives morzer's event JSON: each failed apply, update or
backup, each staged release, and every morning what `doctor` found wrong.
`doctor` fails when Xray cannot reach the internet through the upstream, so a
target at its default level hears about that and not about warnings, and it
says which layer failed: the upstream proxy's address, its credentials, the
destination behind it, or an exit that no longer matches `healthcheck_expect`.
Traffic only ever leaves through the upstream: with it down, clients get
nothing rather than this server's own address. Xray itself has no route out
of the machine: it runs on internal Docker networks only, and a small gate
container forwards the public port to it and carries its traffic to the
upstream, holding the upstream's credentials. Every apply and update, and
every `doctor`, checks that against what runs: the rendered Xray config has no
way out but the upstream and accepts only listed clients, and the containers
publish nothing beyond 80, `https_port` and 53, unprivileged. An update that
breaks it is rolled back, and a change made by hand fails `doctor`. See
morzer's [notifications](https://github.com/morzecrew/morzer/blob/main/pages/docs/operating/notifications.md).

```sh
sudo morzer notify target add https://hooks.example/morzer
```

**Exit IP.** With a static exit IP from the upstream, make the healthcheck ask
an IP-echo service and expect that IP. Xray turns unhealthy, and `doctor`
fails, when the provider moves you to another address:

```sh
sudo morzer config set healthcheck_url=https://api.ipify.org 'healthcheck_expect=^203\.0\.113\.7\s*$'
```

**Monitoring.** For history rather than alerts, point morzer's metrics at the
node exporter's textfile directory: every minute it writes the services and
health checks (`morzer_health_check_ok{check="egress"}`), and after each
scheduled `doctor` every check (`morzer_doctor_check`), which Prometheus keeps
as transitions over time. See morzer's
[monitoring with Prometheus](https://github.com/morzecrew/morzer/blob/main/pages/docs/operating/monitoring-with-prometheus.md).

```sh
sudo morzer config set metrics.textfile=/var/lib/prometheus/node-exporter
```

**What the upstream sees.** It carries every connection, so it sees the
addresses and ports they go to, and when and how much. It does not see
hostnames: this server resolves them over DNS-over-HTTPS (`dns_resolver`),
which itself goes out through the upstream, and hands the upstream addresses
only; a name that cannot be resolved fails rather than going out as a name.
The DNS-over-HTTPS server sees the names instead, from the exit's address. The
name a client's TLS sends in the clear (SNI) can be hidden only by the client,
with Encrypted Client Hello (Chrome or Firefox with DNS-over-HTTPS, for sites
that support it), and plain HTTP shows everything. `resolve=upstream` hands the
upstream the hostnames, as dotdash did before 0.2.0.

**Checking the exit.** `exit-check` asks, through the upstream as client
traffic goes, which IPv4 and IPv6 addresses sites see, and from which network
(ASN) and country. It changes nothing.

```sh
sudo morzer task run exit-check --output
```

"IPv6 unavailable" means the upstream has no IPv6 exit, so sites see IPv4 only;
that is not a leak. "MISMATCH" means both answer from different networks, which
a site reached over both can tell apart; ask the provider for matching IPv6.
An IP checker in a browser that shows an IPv6 address this task calls
unavailable is seeing the device's own, outside the tunnel: route IPv6 through
the tunnel, or turn it off, in the client app. Likewise, a device keeps its
traffic inside the tunnel when the tunnel drops only if its app says so (TUN
mode with a kill switch, or "block connections without VPN" on Android); the
server cannot enforce it.

**DNS on the device.** In an app's VPN or TUN mode the device's DNS goes to
the app. The Xray config from `client-config` answers what reaches it on port
53 over DNS-over-HTTPS (`dns_resolver`) through the tunnel, with IPv4 addresses
only, and a lookup it cannot answer fails rather than going to the local
network's resolver; CI runs it and checks that no DNS packet leaves the
client. IPv4 only, because an app handed an IPv6 address may send it outside a
tunnel that carries IPv4 only; this server reaches sites over IPv4 first
anyway. A link carries no DNS settings, so with links the app's own apply. As
of November 2026:

- **v2rayNG** (Android), with the config imported as a custom config: its VPN
  hands the device's DNS ("VPN DNS", 1.1.1.1 by default) to the config's SOCKS
  inbound on 10808, so keep the app's SOCKS port at 10808. IPv6 is off by
  default, and Android then blocks it rather than leaking it.
- **v2rayN** (desktop): TUN reaches a custom config only with the profile's
  "Socks port" set to 10808, and then answers DNS with v2rayN's own DNS
  settings, so keep those going through the proxy. Its TUN carries no IPv6 by
  default, and its strict route (on by default) blocks it on Windows and
  Linux.
- **Hiddify** reads only the outbounds of an Xray config and drops its DNS and
  routing, so use the links. It answers DNS itself, through the proxy by
  default.
- **iOS:** Happ runs an Xray config as it is but sets the tunnel's DNS itself
  ("Tunnel DNS"); its "Include all networks" keeps the rest of the traffic in
  the tunnel. Streisand and V2Box document neither, so check them with a DNS
  leak test site.

### Canary (optional)

The server cannot tell when a network starts blocking it. The canary is a
second, small bundle from this repository (`canary/`, published as
`ghcr.io/morzecrew/dotdash-canary`) for a machine inside that network, such
as a box at home: it connects as an ordinary client, fetches a URL through
dotdash, and fails `doctor` when it cannot. It needs Docker, sops, age and
morzer (`scripts/bootstrap.sh`), and no open port.

1. On the server, give it a client of its own: a `<uuid> canary` line in
   `sudo morzer secret edit vless_clients`. Revoke it like any device.
2. Print its setup there, and run what it prints on the canary machine:

   ```sh
   sudo morzer task run canary-config --output -- canary
   ```

3. On the canary machine, add a notify target and check every ten minutes:

   ```sh
   sudo morzer notify target add https://hooks.example/morzer
   sudo morzer config set doctor.schedule='*:0/10'
   ```

`canary-config` names the profiles that check more: `xhttp` adds XHTTP over
TLS, and `xhttp-reality` XHTTP with REALITY.

`doctor` then fails on `health endpoints respond` when three tries in a row
cannot fetch `probe_url` through dotdash, and each
failing check notifies again until it is fixed. The canary is released with
dotdash, at the same version: its channels are `dotdash-canary:main` and
`:stable`, signed with this repository's keys.

To compare the transports from that network, `measure` fetches `probe_url`
through each one N times (20 unless given) and prints JSON: how many
succeeded, timed out or failed, and the latency of those that succeeded. It
measures the way through dotdash, not the exit, which `exit-check` on the
server covers.

```sh
sudo morzer task run measure --output -- 50
```

### Moving to a new server

When the server's IP is blocked or the machine is lost, rebuild it elsewhere
from the recovery key and a backup. Client links name the domain, and the keys
come back from the backup, so devices keep the links they have. Prepare for it
now: keep the recovery key off the machine, give morzer a backup target (above),
and set the domain's `A` record TTL to 300 seconds or less.

```sh
# on the new server, after scripts/bootstrap.sh
sudo morzer --product dotdash installation import --from-backup \
  --target s3://bucket/dotdash --credentials-file ./bucket.yaml \
  --identity ~/dotdash-recovery.key
sudo morzer update oci://ghcr.io/morzecrew/dotdash:stable
# optional, keeps Caddy's certificate: the id and installation id import printed
sudo morzer backup fetch <backup id>
sudo morzer restore --force --confirm <installation id> --identity ~/dotdash-recovery.key
```

Then point `example.com`, and `ns.example.com` for the DNS tunnel, at the new
IP, and shut the old machine down: two live servers with one installation id
confuse each other's backups. A `file://` target needs no `--credentials-file`.

## Parameters

| Name | Default | |
| --- | --- | --- |
| `upstream_protocol` | `socks` | `socks` or `http` |
| `upstream_host`, `upstream_port` | required | upstream proxy |
| `upstream_tls` | `false` | connect to the upstream over TLS |
| `upstream_udp` | `false` | relay UDP via a SOCKS5 upstream with UDP ASSOCIATE; otherwise UDP is dropped |
| `https_port` | `443` | host port for REALITY and the site |
| `xdns_domain` | `t` | delegated tunnel zone (`xdns` profile); a name with no dot is under the domain |
| `xdns_bind` | `0.0.0.0` | host address for UDP/53 |
| `xdns_mtu` | `900` | tunnel reply size; lower if replies get lost |
| `xhttp_reality_port` | `8443` | host TCP port for XHTTP with REALITY (`xhttp-reality` profiles); not `https_port` or 80 |
| `log_level` | `error` | Xray error log; access log is always off. `warning` and below name the destinations of failed connections |
| `healthcheck_url` | `https://www.gstatic.com/generate_204` | fetched through the upstream by the healthcheck |
| `healthcheck_expect` | `.*` | regular expression the healthcheck response must match, such as the exit IP |
| `resolve` | `gateway` | who turns hostnames into addresses: `gateway`, this server over `dns_resolver`, so the upstream sees addresses only; `upstream`, the upstream, which then sees every hostname |
| `dns_resolver` | `https://1.1.1.1/dns-query` | the DNS-over-HTTPS server `resolve=gateway` asks, through the upstream, and `client-config`'s Xray config asks through the tunnel; `https://` only |
| `cert_issuer` | `acme` | `acme` (Let's Encrypt) or `internal` (Caddy's own CA, for a machine the internet cannot reach) |
| `site_dir` | `/srv/dotdash` | host directory of your own cover site |
| `servers` | `self` | servers sharing these keys, comma-separated, for client configs; `self` is this one |

Check a change with `morzer release verify ./bundle --render-check`.

## CI

[bundle-ci](https://github.com/morzecrew/bundle-ci) builds, signs and
smoke-tests the bundle on every pull request and push. A push to `main`
publishes `:main`, and a tag `vX.Y.Z` on `main` publishes `:X.Y.Z` and
`:stable` for both bundles and creates one GitHub release from `CHANGELOG.md`
with both signed archives attached. The smoke install (`.github/smoke.d`) runs a stand-in upstream
proxy and `cert_issuer=internal`, then connects clients over REALITY and XHTTP.
Renovate opens a pull request when a pinned image's tag or digest moves, so the
same smoke test gates each bump.

A weekly benchmark, and any pull request that changes the pinned images or
Xray's config, measures REALITY and XHTTP in a rig under added latency and
packet loss (Linux netem, on the client's side only): fetch success, time to
first byte, 1 MiB transfers, and how fast clients get back through after Xray
restarts. A pull request's run summary shows its figures beside the last ones
from `main`, and each run keeps its JSON for 90 days. It informs and never
gates; run it with other parameters from the Actions tab.
